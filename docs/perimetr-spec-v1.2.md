## 1. Суть и границы продукта

### 1.1 Задача

Квалифицированный кандидат с многогранным опытом плохо обслуживается job-бордами: разные грани его опыта релевантны разным ролям, а начиная с уровня среднего менеджмента значительная часть найма происходит без публикации вакансии. «Периметр» решает три задачи, которые кандидат сегодня делает руками:

1. **Находит места работы**, а не только вакансии: компании, у которых по внешним признакам назревает потребность в такой роли.
2. **Сопоставляет** ожидания конкретного работодателя с конкретными фактами из опыта кандидата, честно показывая разрывы.
3. **Готовит контакт**: резюме, переставленное под эти ожидания, и текст обращения — сопроводительное письмо или холодное первое письмо руководителю.

### 1.2 Что продукт делает

- Поиск открытых вакансий и генерация гипотез позиций по профилю кандидата.
- Ручное добавление места: ссылка на вакансию или вставленный текст вакансии.
- Разбор каждого места: 5–7 ключевых ожиданий работодателя против элементов опыта и образования кандидата.
- Формулировка уникального ценностного предложения кандидата для этой компании.
- Генерация резюме под место и текста письма.
- Аудит профиля кандидата по критериям, которые реально влияют на скрининг (квантификация достижений, масштаб управления, прогрессия, перерывы, языки, право на работу), с конкретным списком правок.
- Разделение разрывов на жёсткие блокеры и мягкие гэпы: первые показываются до генерации документов, вторые закрываются переупаковкой резюме и мостом в письме.
- Проверка сгенерированных документов на шаблонность, клише и внутреннюю согласованность до того, как их увидит пользователь.
- Экспорт и синхронизация всей базы найденного в Google-таблицу пользователя.
- Отправка писем (v2).

### 1.3 Что продукт не делает

- Не ведёт переписку за кандидата и не отвечает на входящие письма.
- Не делает массовых рассылок (осознанное ограничение, см. §12.4).
- Не парсит LinkedIn и другие площадки в обход их условий использования: при ручном вводе по ссылке приложение делает один запрос за страницей, которую пользователь и так открыл бы сам, и не обходит защиту от ботов.
- Не хранит и не угадывает личные email-адреса руководителей (см. §10.6).
- Не является ATS и не отслеживает статусы в чужих системах.
- Не обещает «обойти ATS» и не набивает резюме ключевыми словами: приложение делает документы читаемыми для парсера и человека, но каждый термин из вакансии попадает в резюме только при подтверждении в опыте. Совпадение ключевых слов — необходимое, но слабое условие отбора, и подгонка под него без фактов вредит на этапе интервью.
- Не ищет знакомых кандидата в целевых компаниях; фиксирует канал выхода (холодно / тёплый контакт / referral), но контакты для представления пользователь находит сам.

### 1.4 Пользователь

Один пользователь = один кандидат = один Google-аккаунт. Мультитенантность на уровне строк БД, но продукт проектируется как персональный инструмент, не как рекрутинговая платформа.

## 2. Термины

| Термин | Значение |
|---|---|
| **Место** (opportunity) | Единица работы: компания + роль. Бывает двух типов. |
| **Вакансия** (`vacancy`) | Место с опубликованной вакансией, есть источник. |
| **Гипотеза** (`hypothesis`) | Место без опубликованной вакансии: компания, где роль вероятно назреет. |
| **Сигнал** (signal) | Внешнее событие, из-за которого гипотеза правдоподобна: раунд, выход на рынок, реорганизация, уход руководителя, рост, публичные проблемы с операционкой. |
| **Разбор** (analysis) | Набор ожиданий работодателя с привязкой к фактам опыта кандидата. |
| **УЦП** | Уникальное ценностное предложение кандидата для конкретного места. |
| **Профиль** | Резюме + свободные сведения об опыте + структурированные поля (масштаб, право на работу, языки по CEFR, перерывы) + настройки поиска. |
| **Банк фактов** | Атомарные достижения кандидата в формате «действие → как → измеримый итог», извлечённые из профиля и подтверждённые пользователем. Единственный источник содержания для резюме и писем. |
| **Жёсткий блокер** | Требование, которое письмом и переупаковкой не закрыть: нет права на работу без спонсорства, нет обязательной лицензии, нет обязательного местного языка, нет опыта управления людьми на роли руководителя руководителей, кратный разрыв масштаба, зарплата вне вилки. |
| **Мягкий гэп** | Разрыв, который закрывается расстановкой акцентов и мостом в письме: смена отрасли или домена, career gap, недобор лет, частичное несовпадение по инструментам, частые переходы, overqualification, релокация, умеренный разрыв масштаба. |
| **Мост** (bridge) | Абзац письма или строка резюме, прямо закрывающие мягкий гэп; тип моста определяется в разборе. |
| **Верхняя треть** | Первые ~15 строк первой страницы резюме: заголовок, саммари, строка фактов, первые буллиты. Единственная часть, которую гарантированно читают на первичном скрининге. |
| **Swap-тест** | Проверка письма на шаблонность: если заменить компанию и роль на другие и текст не ломается — письмо generic и не отправляется. |
| **Канал** | Способ выхода на компанию: `cold` (холодная подача), `warm` (тёплый контакт), `referral` (представление сотрудником). |

## 3. Пользовательские сценарии

### 3.1 Первый вход

1. Пользователь открывает приложение → «Войти через Google».
2. Google OAuth: запрашиваются `openid`, `email`, `profile`, `drive.file`.
3. После входа: экран профиля. Пусто, есть подсказки.
4. Пользователь вставляет резюме, добавляет свободные заметки, задаёт периметр и настройки.
5. Приложение извлекает из резюме банк фактов и показывает аудит профиля (§10.4a): что в резюме работает на скрининге, чего не хватает, какие структурированные поля заполнить — размер команды и бюджет, право на работу, языки по CEFR, причины перерывов, LinkedIn.
6. Пользователь подтверждает факты и дополняет недостающее. Это разовая работа на 15–30 минут, результат которой используется во всех разборах и документах; без неё модель либо не покажет масштаб и числа, либо их придумает.
7. Приложение создаёт Google-таблицу «Периметр — поиск работы» на диске пользователя и показывает на неё ссылку.

### 3.2 Прогон поиска

1. Кнопка «Найти места».
2. Задача уходит в фон (§9.5), интерфейс показывает статус-бар с этапами.
3. Через 1–3 минуты приходит 6–10 новых мест, они появляются в списке и в таблице.
4. Пользователь просматривает список, лишнее отправляет в архив.

### 3.3 Работа с местом

1. Клик по месту → карточка: компания, роль, сигнал, источник.
2. «Разобрать ожидания» → 5–7 ожиданий с весом и привязкой к фактам, шкала закрытия, жёсткие блокеры (если есть), мягкие гэпы с типом моста, УЦП, главное возражение работодателя.
3. Если найден жёсткий блокер — карточка показывает его первым и предлагает два действия: «в архив» или «снять уточнением профиля» (например, право на работу есть, но не заполнено → интерфейс ведёт в поле, разбор пересчитывается). Кнопки генерации при неснятом блокере доступны, но с предупреждением: письмо на такое место расходует попытку и почти никогда не работает.
4. «Собрать резюме» → версия резюме под это место в формате страны, редактируемая; рядом — замечания автоматических проверок (§10.10).
5. «Написать письмо» → сопроводительное (для вакансии) или холодное (для гипотезы), редактируемое; рядом — результат swap-теста и стоп-листа.
6. Пользователь правит текст руками; проверки перезапускаются; статус меняется на «готово к отправке».
7. Пользователь указывает канал: холодная подача, тёплый контакт или referral, и имя того, кто может представить (§12.4).
8. Скачивает DOCX/PDF или отправляет письмо из интерфейса (v2).

### 3.4 Ручное добавление вакансии

Кандидат нашёл вакансию сам — на job-борде, в телеграм-канале, от знакомого.

1. Кнопка «Добавить вакансию» → поле для ссылки **или** поле для текста.
2. Если ссылка: воркер загружает страницу, вычищает разметку, извлекает текст (§10.9). Не получилось — приложение честно говорит, что страница закрыта, и просит вставить текст.
3. Модель извлекает из текста структуру: компания, роль, город, требования, ссылка на источник.
4. Пользователь видит распознанное, правит при необходимости, подтверждает.
5. Место создаётся со статусом `new` и типом `vacancy`, дальше — обычный сценарий 3.3.

Отличие от найденных мест: разбор ожиданий строится на **реальном тексте вакансии**, а не на догадках о роли. Это самый точный вход в продукт, и он же — самый дешёвый по AI.

### 3.5 Работа через таблицу

Пользователь открывает Google-таблицу, сортирует и фильтрует по-своему, меняет статус или добавляет комментарий в отведённых колонках. При следующем открытии приложения изменения подхватываются (§11.4).

### 4.1 Стек

| Слой | Решение | Почему |
|---|---|---|
| Фронтенд | React 18 + Vite + TypeScript | Один разработчик, быстрая сборка |
| Хостинг фронта | Cloudflare Pages | Один домен с воркером — нет CORS и third-party cookies |
| Бэкенд | Cloudflare Workers | Нужен только как прокси и хранилище логики; холодного старта нет |
| БД | Cloudflare D1 (SQLite) | Объём данных на пользователя — единицы мегабайт |
| Сессии, кэш | Cloudflare KV | TTL из коробки |
| Фоновые задачи | Cloudflare Queues | Поиск идёт 1–3 минуты, превышает удобный лимит HTTP-запроса |
| AI | OpenAI Responses API | Structured Outputs + встроенный web search |
| Хранилище файлов | R2 (только для DOCX/PDF, v2) | |

Домен один: `perimetr.app` отдаёт SPA, `perimetr.app/api/*` перехватывается воркером. Это устраняет проблемы с cookie и CORS.

### 4.2 Переиспользование из семейства Twin

**[1.2 · Twin]** «Периметр» — четвёртое приложение семейства. Три предыдущих работают в проде:

| Приложение | Что это | Что в нём проверено |
|---|---|---|
| **twin** | личный трекер задач с ИИ-ассистентом; GitHub Pages + Firestore + Cloudflare Worker | многослойный контекст для LLM, классификатор перед дорогим вызовом, CRUD-действия модели через JSON-блоки, редактор промптов, трёхшаговый агент «план → исследование → компиляция» |
| **twin-things** | совместный каталог вещей, массовый AI-импорт по фото и тексту | таксономия из БД в промпт, санитайз ответа модели по закрытым спискам id, пайплайн «разобрал → показал чек-лист → сохранил после подтверждения», 45 тестов чистого ядра |
| **Help_me_clean** | детская уборка через камеру | строгая JSON-схема с одним повтором и санитайзом, серверный дневной бюджет на ИИ, i18n с языком вывода модели как параметром промпта, 157 тестов чистого ядра |

Стек «Периметра» отличается принципиально и сознательно: React/TS вместо ванильных ES-модулей, D1 вместо Firestore, собственный OAuth вместо Firebase Auth, очереди вместо fire-and-forget в браузере. Поэтому **дословного копирования файлов здесь будет мало — на день работы, не больше**, и притворяться иначе не нужно. Ценность в другом: три вещи переносятся независимо от стека, и каждая из них дорога в разработке с нуля и дёшева в переносе:

1. **Контракт вызова LLM** — строгая схема → парс → один повтор → санитайз → непустой фолбэк, промпты и пороги в редактируемом конфиге, язык вывода отдельным параметром.
2. **Дисциплина «чистое ядро + `node --test`»** — вся детерминированная логика в модулях без сети и БД, покрытых тестами без единой зависимости.
3. **Тонкий воркер, у которого ключ модели не покидает сервер ни при каких условиях.**

#### 4.2.3 Что сознательно не переиспользуется

- **Firebase целиком** (Auth, Firestore, Storage, правила). «Периметру» нужен Google OAuth ради `drive.file`, а не ради Firebase Auth; данные реляционные и локальные для одного пользователя — D1 подходит лучше, чем документная база. Правила безопасности Firestore заменяются одним инвариантом «`user_id` из сессии в каждом запросе» (§15.1), и это проще.
- **Клиентские вызовы модели.** В трёх приложениях промпты живут в браузере, а воркер — тонкий прокси. Здесь так нельзя: промпты содержат резюме, а проверки §10.10 и валидация §10.4 должны быть недоступны правке из консоли. Вся работа с моделью — в воркере.
- **`voice.js` как модуль.** Он не ES-модуль (IIFE, вешает глобалы на `window`) и в React-сборку не встанет как есть. Переносится идея и код распознавания, не файл.

### 4.3 Чем уже заплачено: находки из трёх работающих приложений

**[1.2 · Twin]** Четыре места, где семейство наступило на грабли. Все четыре относятся к «Периметру».

1. **Существующий воркер `task-intake-worker` переиспользовать нельзя — нужен свой.** Его `/ai` защищён только проверкой `Origin` (twin → `worker/task-intake-worker.js:48-58`): сессии нет, и любой, кто открыл страницу twin, может гонять ключ OpenAI из консоли. Для личного трекера задач это осознанный размен; здесь — нет: в промптах резюме (персональные данные, §15.2), а расход считается по `usage_log` на пользователя (§10.9). Общий воркер означал бы, что месячный лимит и spend limit считают чужой трафик, а §18.1 формально проходит при фактически доступном ключе. **Отдельный воркер, отдельный project-ключ OpenAI, отдельный spend limit.**
2. **Тихий отказ ИИ — реальный, а не гипотетический режим.** В twin задокументировано: сводка по тегу обновляется после сохранения задачи, и «если ключ OpenAI не задан, шаг молча пропускается, ошибка не показывается». Пользователь считает, что фича работает. Отсюда — §13.2 с четырьмя обязательными состояниями не факультативен, и `usage_log` (§7) должен писать **и неудачные вызовы тоже**, иначе «потрачено $0» будет означать и «всё дёшево», и «ничего не работает».
3. **Заявленная параллельность оказалась последовательным циклом.** Документация twin описывает deep research как «до 5 параллельных исследовательских потоков», а код (twin → `task.html`, `aiDraft()`) выполняет `for (const item of plan) { await callGPT(...) }` — строго по очереди. При пяти областях это пятикратное время. §9.1 «Ищу открытые вакансии (N запросов)» рискует повторить это при p95 < 180 с (§14): закладывайте `Promise.all` с ограничением параллелизма (3–4 одновременно, чтобы не поймать 429) **в код с самого начала**, и внесите ограничитель в конфиг рядом с моделями.
4. **Пространство имён данных задаётся один раз и в начале.** twin начинал писать в корень Firestore и позже был вынужден сделать разовую миграцию всех данных под `apps/twin/users/{uid}/` (`store.js`, `migrateIfOwner`), причём легаси-коллекции в корне остались навсегда. Аналог для D1 — миграции: заведите механизм версионированных миграций схемы на Этапе 0, когда таблиц семь, а не на Этапе 3, когда в них данные.

## 5. Аутентификация

### 5.1 Схема

Google OAuth 2.0, Authorization Code Flow с PKCE. Обмен кода на токены выполняет **воркер**, не браузер: `client_secret` в браузер не попадает.

```
Браузер          Воркер                Google
   │ GET /api/auth/start │                 │
   │───────────────────►│ генерирует state+PKCE, кладёт в KV (TTL 10 мин)
   │◄─── 302 на accounts.google.com ───────►│
   │                    │                  │ пользователь даёт согласие
   │◄─── 302 /api/auth/callback?code=… ────│
   │───────────────────►│ обмен кода на токены (client_secret)
   │                    │ сохраняет refresh_token (шифрованный) в D1
   │◄─ Set-Cookie: sid ─│ создаёт сессию в KV
```

### 5.2 Scopes

| Scope | Зачем | Категория Google | Этап |
|---|---|---|---|
| `openid`, `email`, `profile` | идентификация | базовый | MVP |
| `drive.file` | создать и вести **свою** таблицу | не sensitive | MVP |
| `gmail.compose` | создать черновик письма | restricted | v2 |

**Важное ограничение, влияющее на план.** `drive.file` даёт доступ только к файлам, созданные самим приложением, и не требует верификации Google — поэтому таблицу создаёт приложение, а не пользователь. Scope `spreadsheets` (доступ ко всем таблицам) — sensitive, требует верификации; он не нужен.

`gmail.compose` и `gmail.send` — restricted scopes: требуют верификации приложения и ежегодного CASA-аудита. Пока приложение в режиме Testing, оно работает без верификации для до 100 тестовых пользователей, **но refresh-токены в этом режиме протухают через 7 дней** — пользователю придётся перелогиниваться раз в неделю. Отсюда решение: MVP живёт на `drive.file` (Testing-режим или верификация не нужны), а Gmail добавляется только вместе с прохождением верификации либо не добавляется вовсе (альтернативы в §12).

### 5.3 Сессии

- Cookie `sid`: HttpOnly, Secure, SameSite=Lax, TTL 30 дней, значение — случайные 32 байта.
- В KV: `session:<sid>` → `{user_id, created_at, last_seen}`, TTL 30 дней, продление при активности.
- Выход: удаление ключа KV + очистка cookie. «Выйти на всех устройствах» — удаление всех сессий пользователя (индекс `user_sessions:<user_id>`).
- CSRF: все мутирующие запросы требуют заголовок `X-Perimetr-CSRF` со значением из non-HttpOnly cookie (double submit) — либо SameSite=Strict, если приложение не открывается по внешним ссылкам.

### 5.4 Хранение токенов Google

- `refresh_token` шифруется AES-GCM ключом `TOKEN_ENC_KEY` (секрет воркера) перед записью в D1.
- `access_token` не хранится в БД — держится в KV с TTL, равным сроку жизни минус 60 секунд.
- При `invalid_grant` (пользователь отозвал доступ) — помечаем `google_reauth_required = 1`, интерфейс показывает баннер с повторным входом.

## 6. Хранение секретов

Все секреты — через `wrangler secret put`, ни один не попадает в репозиторий, в `wrangler.toml` и в бандл фронтенда.

| Секрет | Назначение |
|---|---|
| `OPENAI_API_KEY` | Ключ OpenAI. **Никогда** не отдаётся клиенту. |
| `GOOGLE_CLIENT_ID` | Публичный, но держим рядом |
| `GOOGLE_CLIENT_SECRET` | Обмен кода на токены |
| `TOKEN_ENC_KEY` | Шифрование refresh-токенов (32 байта base64) |
| `SESSION_PEPPER` | Хеширование идентификаторов сессий в логах |

Дополнительно на стороне OpenAI: отдельный project-ключ только под это приложение, установлен месячный spend limit, включены алерты. При компрометации ключ отзывается в панели OpenAI и заменяется одной командой `wrangler secret put` без передеплоя фронта.

**[1.2 · Twin]** «Отдельный project-ключ только под это приложение» — не формальность, а прямой вывод из §4.3.1: в семействе уже есть общий воркер `task-intake-worker` с эндпоинтом `/ai`, которым пользуются три приложения, и защищён он только проверкой `Origin`. Соблазн «воркер же есть, добавим маршрут» здесь надо отклонить явно, поэтому в таблице секретов подразумевается **свой** воркер `perimetr-api` со своим ключом. Формулировка Origin-проверки берётся из рабочего кода (twin → `worker/task-intake-worker.js:48-58`) с одной важной деталью: хост разбирается через `new URL(origin).hostname` и сравнивается целиком — сравнение подстрокой пропускает `https://evil-localhost.example`. В «Периметре» Origin-проверка не заменяет сессию, а дополняет её.

  work_auth    TEXT DEFAULT '',                    -- JSON: [{region, status: citizen|permit|needs_sponsorship}]
  relocation   TEXT DEFAULT '',                    -- JSON: {ready: yes|no|conditional, package_needed: bool}

  source_date   TEXT,

  channel       TEXT NOT NULL DEFAULT 'cold',      -- cold | warm | referral (§12.4)
  referral_name TEXT,                              -- кто может представить; редактируется и в таблице
  salary_hint   TEXT,                              -- вилка из вакансии, если указана; для фильтра блокеров

  contact_email TEXT, contact_linkedin TEXT,

);
CREATE INDEX idx_doc_opp ON documents(opportunity_id, kind, version DESC);

CREATE TABLE runs (                  -- прогоны поиска
  id          TEXT PRIMARY KEY,
  user_id     TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,

  added       INTEGER DEFAULT 0,     -- после дедупа

CREATE TABLE usage_log (             -- учёт расходов на AI
  id        TEXT PRIMARY KEY,
  user_id   TEXT NOT NULL,
  operation TEXT NOT NULL,           -- discover | analyse | resume | letter

```

Правила версионирования документов: новая генерация создаёт новую версию, старые сохраняются. Правки пользователя пишутся поверх текущей версии с `edited_by_user = 1`; повторная генерация поверх отредактированного вручную требует подтверждения в интерфейсе.

Дедупликация: `company_key` = нижний регистр, без юридических форм (AB, AS, GmbH, Ltd, Inc, ООО), без пунктуации. Совпадение `company_key` + похожая роль (расстояние Левенштейна по нормализованному названию < 0.2) считается дублем и не добавляется.

## 9. Фоновые задачи

### 9.1 Прогон поиска

1. `POST /api/runs` создаёт запись `runs` в состоянии `queued`, кладёт сообщение в Queue, возвращает `run_id`.
2. Consumer-воркер выполняет этапы, обновляя `runs.stage` после каждого:
   - `Формирую поисковые запросы`
   - `Ищу открытые вакансии` (N запросов)
   - `Ищу компании с сигналами` (N запросов)
   - `Проверяю на дубли`
   - `Записываю в таблицу`
3. Клиент подписан на SSE и рисует статус-бар с этими этапами и счётчиком секунд.
4. Итог: `state = done`, `added = k`. При ошибке `failed` + `error` с человеческим текстом.

**[1.2 · Twin]** Два уточнения из работающего кода.

- **Этапы объявляются данными, а не рисуются вручную.** В twin (`task.html`, `aiDraft()`) трёхшаговый агент держит шаги массивом `[{id, icon, label}]`, из него рендерится список, и каждый шаг переводится в состояние функциями `stepActive(id)` / `stepDone(id)`. Тот же массив служит источником текстов для SSE. Для §9.1 это значит: список этапов — одна константа в конфиге воркера, клиент рисует её до старта прогона (сразу видно, сколько шагов впереди), а SSE присылает только `stage_id` и время. Это же снимает риск рассинхрона названий этапа между воркером и SPA.
- **Веб-запросы этапа «Ищу открытые вакансии» выполнять параллельно с ограничением.** В twin аналогичный многошаговый агент вопреки собственной документации ходит по областям последовательным `for … await` (§4.3.3). При N ≈ 6 и p95 < 180 с (§14) последовательный обход почти наверняка не уложится. Закладывайте пул на 3–4 одновременных запроса (больше — риск 429 у OpenAI, §16), величину — в конфиг рядом с `MODELS`.

### 9.2 Ограничения и защита

- Не более одного активного прогона на пользователя; повторный запрос возвращает существующий `run_id`.
- Не более 10 прогонов в сутки на пользователя.
- Таймаут прогона — 5 минут; после — `failed`.
- Идемпотентность: сообщение в очереди содержит `run_id`, повторная доставка не создаёт дублей (проверка состояния перед стартом).

Назначение по операциям:

| Операция | Модель | Обоснование |
|---|---|---|
| Discover (поиск мест) | `gpt-5.6-terra` + web search | Нужен поиск и рассуждение о сигналах, но не флагман |
| Analyse (разбор) | `gpt-5.6-sol` | Ядро ценности продукта, экономить нельзя |

| Letter | `gpt-5.6-terra` | То же |

| Проверки документов, swap-тест | `gpt-5.6-luna` + правила в воркере | Дешёвая семантическая проверка поверх кодовых правил (§10.10) |

Модели вынесены в конфиг `MODELS = {discover, analyse, resume, letter, extract, audit, check}` — замена без правки логики. Обязателен fallback: при 429/503 повторить с экспоненциальной задержкой (3 попытки), затем деградировать на модель ступенью ниже и пометить результат `degraded: true`.

**[1.2 · Twin] Конфиг шире моделей, и у него должен быть экран.** ТЗ обещает конфигурируемость в трёх местах: модели здесь, пороги аудита и проверок в §19, стоп-лист «ведётся в конфиге воркера» в Приложении Б. Если конфиг — это константы в исходнике, то каждое из этих обещаний означает передеплой: добавить одно слово в стоп-лист по замечанию пользователя, подвинуть порог квантификации с 60% на 50% по итогам первых двух недель (§19) — коммит, сборка, выкладка. При заявленном режиме «ревизия порогов через две недели ручной оценки» это гарантированно не будет сделано.

В twin эта задача решена и работает: `prompts.js` держит **дефолты в коде**, переопределения — в документе БД, а `admin.html` — экран, где каждый промпт лежит в `textarea` рядом со списком доступных ему токенов, бейджем «изменён» и кнопками Save / Reset. Подстановка живых данных — `fillPrompt(key, tokens)`, простая замена `{{TOKEN}}`: шаблон правится текстом, а сборка контекста остаётся в коде. Убрал токен из шаблона — просто выпал этот блок данных, приложение не сломалось.

**Предложение.** Завести один конфиг-документ на четыре ключа и один служебный экран:

| Ключ конфига | Содержимое | Кто правит |
|---|---|---|
| `MODELS` | карта операция → модель (эта таблица) + `maxConcurrency` для §9.1 | владелец |
| `THRESHOLDS` | пороги §10.4a и §10.10: доля буллитов с числом, ×3/×10 для масштаба, диапазоны длины писем, минимум предложений в swap-тесте, месячный лимит §10.9 | владелец |
| `STOPLIST` | Приложение Б, по языкам (`en`, `ru`, `sv`) + запрещённые начала писем | владелец |
| `PROMPTS` | шаблоны Discover / Analyse / Resume / Letter / Audit / Ingest / Check с токенами `{{PROFILE}}`, `{{FACTS}}`, `{{JD}}`, `{{SIGNAL}}`, `{{EXPECTATIONS}}` | владелец |

Дефолты — в коде воркера, переопределения — в таблице `config (key TEXT PRIMARY KEY, value TEXT, updated_at TEXT)`, эффективное значение = переопределение или дефолт. Доступ — только владельцу приложения (`GET`/`PUT /api/admin/config`), не пользователю: это не пользовательская настройка. Стоимость — примерно день работы, и она окупается на первой же ревизии порогов. Экран уместен в **Этапе 1**, а не в пятом: без него §19 не выполнится.

### 10.2 Общие правила вызова

- Только Responses API со Structured Outputs (`response_format: json_schema`, `strict: true`) — парсинг текста руками не допускается.
- Профиль кандидата ставится в начало промпта и не меняется между вызовами → работает кэширование входа, экономия до 90% на повторных запросах.
- `store: false` — история не хранится на стороне OpenAI.
- Каждый вызов логируется в `usage_log` с токенами и расчётной стоимостью.
- Таймаут вызова 120 секунд, `AbortController` обязателен.

**[1.2 · Twin] Контракт вызова — один на все операции.** В Help_me_clean он реализован как `jsonCall(payload, sanitize, isEmpty)` (`js/ai.js`) и звучит так: строгая схема → парс → **если результат пуст, ровно один повтор с `temperature: 0`** → санитайз → непустой фолбэк, из которого вызывающий код всегда получает объект нужной формы и никогда — исключение. Structured Outputs этот контракт не отменяет, а укорачивает: схема гарантирует форму ответа, но не то, что `fact_id` существует в банке, `bridge` — из закрытого списка §10.4, а `kind` блокера — один из шести. Именно поэтому §10.4 уже требует валидации после генерации; предложение — оформить её как **одну общую ступень пайплайна**, а не как отдельную проверку внутри каждой операции:

```
callModel(op, tokens) → schema → parse → retry(1) → sanitize(op) → validate(op) → log(usage)
```

Где `sanitize(op)` — чистая функция (приводит к схеме, выбрасывает значения вне закрытых списков), `validate(op)` — правила ТЗ (проверка `source_hint` в тексте профиля, снятие блокеров структурированными полями, пересчёт `score` воркером). Обе — без сети, обе тестируются в Node (§10.10). В Help_me_clean санитайзеры живут в `family-core.js` отдельно от `ai.js` ровно по этой причине.

**[1.2 · Twin] Классификатор перед дорогим вызовом.** ТЗ ставит профиль в начало промпта ради кэширования — это верно и это надо сохранить. Но у `Analyse` (`gpt-5.6-sol`, ядро стоимости) на входе «профиль целиком» плюс банк фактов, который у кандидата с 15-летним опытом легко даст 60–100 записей, плюс `jd_text`. Из них к конкретной вакансии относятся 15–25. В twin эта же задача решена дешёвым первым шагом: отдельный вызов `temperature: 0, max_tokens: 250` определяет тему и релевантные объекты, и только потом собирается большой контекст.

Перенос с поправкой на кэширование: **префикс промпта не меняется** (профиль + полный банк фактов в стабильном порядке — кэшируется, скидка до 90%), а результат классификатора едет **суффиксом** как список указателей: «в первую очередь рассмотри факты f12, f18, f31, f44». Кэш цел, внимание модели сфокусировано, стоимость дополнительного вызова на `gpt-5.6-luna` — доли цента. Побочная выгода важнее экономии: чем меньше фактов конкурируют за одно ожидание, тем реже модель приписывает достижение не той роли, а это прямо влияет на §10.4 (валидация `source_hint`) и на критерий приёмки 5.

Для `Resume` и `Letter` тот же приём даёт больше: там факты уже отобраны разбором (`expectations[].fact_id`), и передавать весь банк не нужно вовсе.

### 10.3 Операция Discover

**Вход:** профиль, список уже собранных компаний (для исключения), `breadth`, желаемое количество.

**Промпт (система):** роль консультанта по трудоустройству руководителей; задача — найти места работы; требования: реальные компании; проверяемые источники; смесь вакансий и гипотез в пропорции, зависящей от `breadth`; гипотеза обязана опираться на конкретный датированный сигнал не старше 6 месяцев; запрет на выдумывание контактов.

### 10.4 Операция Analyse

**Вход:** профиль целиком, место, сигнал, тип места и — если есть — `jd_text` (текст вакансии из ручного ввода).

Две ветки промпта. При наличии `jd_text` ожидания **извлекаются из текста вакансии** и ранжируются по важности, догадки запрещены. Без `jd_text` ожидания реконструируются по роли, отрасли, размеру компании и сигналу, и в интерфейсе помечаются как реконструкция. Это разные по надёжности результаты, и пользователь должен видеть разницу.

**Задача:** сформулировать 5–7 ожиданий работодателя, ранжировать их по весу, привязать к каждому конкретный факт из банка фактов (§10.4a) или текста профиля, разделить разрывы на жёсткие блокеры и мягкие гэпы и сформулировать главное возражение — как риск, который нанимающий видит в кандидате.

**Как думает нанимающий, и что из этого обязан проверить разбор.** Найм руководителя для компании — дорогая ставка, и первичный отбор устроен как отсев рисков, а не как поиск достоинств. Скринер ищет три вещи: прогрессию (промоушены, рост охвата), масштаб (люди, деньги, рынки) и связность истории без необъяснённых аномалий; отторжение вызывают противоречия, необъяснённые переходы, отсутствие любых упоминаний работы с людьми на senior-роли и общие формулировки. Поэтому помимо ожиданий из текста вакансии разбор всегда содержит четыре измерения, даже если вакансия о них молчит:

| Измерение | Откуда у работодателя | Откуда у кандидата | Правило воркера |
|---|---|---|---|
| Масштаб управления | размер команды, менеджеры в подчинении, бюджет/P&L, география — из `jd_text` или оценка по размеру компании | `profile.scale` | отношение требуемого к имеющемуся: ≤ 2 → мягкий гэп, ≥ 3 по команде или ≥ 10 по бюджету → жёсткий |
| Право на работу | страна места, упоминание спонсорства в `jd_text` | `profile.work_auth` | статус для региона `citizen`/`permit` → блокера нет; `needs_sponsorship` и вакансия не даёт спонсорства → жёсткий |
| Язык | язык вакансии и явные требования; если вакансия на местном языке и роль клиентская или операционная — местный язык считается обязательным | `profile.languages` | требуемый язык ≥ C1 → нет гэпа; B2 → мягкий; ниже или нет → жёсткий, если язык обязателен |
| Прогрессия и связность | неявно всегда | даты ролей, `profile.gaps`, средний срок в роли | перерыв > 12 мес. без причины, средний срок < 24 мес. → мягкий гэп с соответствующим мостом |

Правила воркера имеют приоритет над моделью: если структурированное поле профиля снимает блокер, воркер удаляет его из ответа модели; если поле пустое — блокер помечается `resolvable_by_profile = true`, и интерфейс ведёт пользователя к полю.

**Классификация разрывов.** Каждое несовпадение получает класс.

- `hard` — жёсткий блокер. Закрытый список из шести: (1) нет права на работу, вакансия не даёт спонсорства; (2) нет лицензии или сертификата, обязательного юридически или регуляторно (если он «желателен» — мягкий гэп); (3) нет обязательного местного языка, и роль его реально требует; (4) роль — руководитель руководителей, у кандидата нет опыта управления людьми (если роль допускает «lead without authority» — мягкий); (5) кратный разрыв масштаба; (6) зарплатные ожидания существенно выше указанной вилки. Письмом и переупаковкой это не закрывается — попытки «уговорить» почти не работают и расходуют контакт.
- `soft` — мягкий гэп. Закрывается мостом в письме и акцентами в резюме: смена отрасли или домена, career gap, недобор лет («8+» против 6 — обычно wish list, а не фильтр), частичное несовпадение по инструментам, частые переходы (штрафуются в нетехнических ролях, почти не штрафуются в техе), overqualification, релокация, умеренный разрыв масштаба (×1,5–2).

Для каждого мягкого гэпа модель называет тип моста — он затем используется в резюме и письме (§10.5, §10.5a):

| `bridge` | Гэп | Что делает мост |
|---|---|---|
| `transferable_metrics` | смена отрасли/домена | достижения переводятся в метрики, одинаково читаемые в обеих отраслях: числа переносятся между отраслями, титулы — нет |
| `trajectory` | умеренный разрыв масштаба | показывает рост масштаба как траекторию и управление сложностью, а не размер как таковой |
| `explained_gap` | career gap | короткая причина перерыва; обучение — лучшая из причин по данным |
| `grouped_roles` | частые переходы, контракты | группировка проектных ролей под одним заголовком, логика переходов (реорг, поглощение, проектная природа) |
| `deliberate_choice` | overqualification | снимает страх «уйдёт, заскучает, дорогой»: почему именно эта роль — осознанный выбор |
| `analogous_tools` | стек / инструменты | аналогичные инструменты + скорость освоения; точные названия из вакансии только там, где правда |
| `relocation_ready` | локация | готовность к релокации и, если применимо, отсутствие потребности в релокационном пакете |
| `results_over_years` | недобор лет | компенсация масштабом и результатами |

**Главное возражение** формулируется как риск нанимающего («уйдёт через год», «не потянет масштаб», «не знает нашу отрасль», «дорого») с ответом, который затем становится обязательным элементом письма. Не «слабое место резюме», а «чего боится тот, кто решает».

**Вес ожиданий.** `must` — из раздела требований или из обязательных измерений выше; `important` — из обязанностей; `nice` — «желательно», «плюсом будет». Первые 3–4 буллита резюме и второй абзац письма строятся под `must`.

```json
{
  "expectations": [
    {
      "expectation": "что работодатель будет ждать от человека на этой роли",
      "weight":      "must | important | nice",
      "evidence":    "конкретный факт, закрывающий это",
      "fact_id":     "id факта из банка, если факт оттуда; иначе null",
      "source_hint": "откуда в профиле взят факт — цитата 3–8 слов",
      "strength":    "strong | partial | gap",
      "gap_class":   "hard | soft | null",
      "bridge":      "тип моста для soft, иначе null",
      "gap_answer":  "если gap — что предъявить взамен, одной фразой"
    }
  ],
  "blockers": [
    { "kind": "work_auth | license | language | no_people_mgmt | scale | salary",
      "detail": "в чём именно", "resolvable_by_profile": false }
  ],
  "score": 0,
  "uvp": "2–3 предложения: что кандидат делает лучше типичного претендента на эту роль, с числом и масштабом",
  "objection": { "risk": "как его видит нанимающий", "answer": "чем снимается" },
  "reconstructed": false
}
```

**Валидация после генерации (антигаллюцинация):** для каждого `evidence` со `strength != "gap"` воркер проверяет, что `source_hint` действительно встречается в `resume_text` или `extras_text` (нормализованное вхождение, допускается до 30% расхождения), а `fact_id`, если указан, существует и подтверждён. Не прошедшие проверку понижаются до `gap` с пометкой «не подтверждено профилем» — это дешевле и надёжнее, чем просить модель «не выдумывать». Блокеры сверяются со структурированными полями профиля по правилам таблицы выше.

`score` пересчитывается воркером, а не берётся у модели: `100 × Σ(w·s) / Σ w`, где `w` = 3 / 2 / 1 для `must` / `important` / `nice`, `s` = 1 / 0,5 / 0 для `strong` / `partial` / `gap`. Жёсткий блокер **не обнуляет** `score`, а выводится отдельным флагом: пользователь должен видеть «совпадение 78%, но блокер — язык», а не необъяснимые 30%. В таблице (§11.2) блокер занимает отдельную колонку.

### 10.4a Операция Profile Audit и банк фактов

Качество всех документов ограничено качеством исходного профиля: если в резюме нет чисел, масштаба и прогрессии, модель их либо не покажет, либо придумает. Поэтому первая AI-операция после заполнения профиля — не поиск, а аудит. Он же даёт кандидату отдельную ценность: список правок, которые улучшают его резюме независимо от приложения.

**Шаг 1. Извлечение банка фактов.** Модель разбирает `resume_text` и `extras_text` на атомарные факты формата «действие → как → измеримый итог» (таблица `facts`). Число выделяется в `metric_value` / `metric_unit`; факты без числа получают `quantified = 0`. Каждому факту — `source_hint`, проверяемый воркером по правилу §10.4; факты без подтверждённого `source_hint` отбрасываются молча. Пользователь видит список, правит и подтверждает; неподтверждённые факты в документы не попадают. Модель также предлагает, к каким фактам без числа число вероятно существует («сколько человек было в команде?», «на сколько сократили срок?») — это вопросы пользователю, а не догадки.

**Шаг 2. Оценка по чек-листу скрининга.** Метрики считает воркер по правилам; модель пишет только текстовые рекомендации поверх них.

| Проверка | Правило (пороги в конфиге) | Почему это важно скринеру |
|---|---|---|
| Квантификация | ≥ 60% подтверждённых фактов с числом; ≥ 2 квантифицированных факта на каждую роль последних 10 лет | измеримые результаты — самый сильный сигнал снижения риска; список обязанностей вместо них — самый частый провал |
| Масштаб | заполнены `scale.team_max` и хотя бы одно из `budget_max` / `pnl` / `geo_scope`; ≥ 1 факт с `scale_tags` на каждую руководящую роль | на middle+ отсутствие масштаба читается как индивидуальный вклад |
| Прогрессия | ≥ 1 промоушен или рост охвата между ролями виден по фактам и датам | даты скринер проверяет именно на прогрессию |
| Управление людьми | ≥ 1 факт с тегом `team` или `managers` для ролей уровня Head / Director | отсутствие любых упоминаний работы с людьми на senior-роли — красный флаг |
| Перерывы | все перерывы > 6 мес. имеют причину в `profile.gaps` | указание причины заметно повышает отклик; резкое падение отклика начинается с перерывов около 3 лет |
| Частота переходов | средний срок в роли < 24 мес. → рекомендация группировки и объяснения | штрафуется в нетехнических функциях |
| Языки | каждый язык с уровнем CEFR | стандарт ЕС; «fluent» не сравнивается с требованием |
| Право на работу | заполнено для каждого региона из `geo` | главное сомнение при международной подаче; снимается одной строкой |
| Возраст ролей | роли старше 15 лет свёрнуты в одну строку | длина: две страницы для 10+ лет опыта, каждая строка должна зарабатывать место |
| LinkedIn | самооценка по чек-листу: summary > 1000 знаков, все роли описаны, фото, ≥ 300 контактов, 3–7 рекомендаций, часть — от прямых подчинённых; `linkedin_url` указан | комплексный профиль заметно повышает отклик, пустой — хуже, чем никакого; большинство рекрутеров сверяют LinkedIn с заявкой. Эффект слабеет с ростом уровня роли, но проверка соответствия остаётся |
| Орфография | проверка словарём языка резюме | ошибки — одна из главных причин мгновенного отказа |

**Результат** — список конкретных задач для пользователя, отсортированных по эффекту («добавьте число к достижению X», «укажите размер команды в роли Y», «объясните перерыв 2021–2022», «заполните право на работу для Германии»), сохраняется в `profiles.audit` и показывается на экране профиля. Кнопка поиска не блокируется; индикатор заполненности учитывает аудит. Аудит перезапускается по кнопке после существенной правки профиля.

**Стоимость:** $0.05–0.10 за прогон, разово или редко.

**[1.2 · Twin] Экран подтверждения фактов уже написан дважды.** Пайплайн «модель разобрала → пользователь видит черновики списком с чекбоксами → сохраняются только отмеченные» реализован в twin-things (`add-item.html`, AI-импорт вещей по фото) и в twin (bulk import на `add-task.html`, редактируемые предложения подзадач). Формы данных разные, а поведение — то самое, что требуют §10.4a шаг 1 и §3.4 шаг 4: ничего не пишется в базу без явного подтверждения, каждая строка правится на месте, отклонённое просто не сохраняется. Стоит посмотреть на рабочие экраны прежде, чем проектировать свой: там уже решены мелочи, которые всплывают только на практике — что делать с частично заполненной строкой, как показать, что модель не уверена, и почему кнопка «сохранить всё» без чекбоксов приводит к базе, засорённой мусором (тот же вывод, что и в §10.8 шаг 3).

### 10.5 Операция Resume

**Вход:** профиль, банк фактов (только `confirmed = 1`), место, разбор.

**Принцип.** Резюме под место — не новый текст, а перестановка подтверждённых фактов под ожидания конкретного работодателя. Модель выбирает и упорядочивает факты и пишет связки; числа и масштаб берутся из банка фактов без изменений. Правило единственного источника: чего нет в `facts` или тексте профиля, того нет в резюме. Ответ — `facts_used` с id использованных фактов.

**Как физически читает скринер и что из этого следует.** На первичном проходе рекрутер тратит порядка 6–7 секунд и идёт по опорным точкам: имя → текущая должность и компания → предыдущая должность и компания → даты (проверка прогрессии) → образование; остальное — сканирование ключевых слов в F-паттерне. На шортлисте резюме читают минуты, но до шортлиста доходит верхняя треть первой страницы. Отсюда структура (порядок секций фиксирован):

1. **Заголовок роли** на языке вакансии, близкий к названию роли из ожиданий.
2. **Саммари 2–3 строки** — ценность для этой роли с числом и масштабом. Не objective («ищу позицию…» — снижает отклик), а что кандидат даёт. Ключевой механизм скрининга — дистанция между саммари (что кандидат хочет, чтобы о нём думали) и буллитами (что он может подтвердить): если саммари заявляет лидерство, а буллиты показывают индивидуальное исполнение, саммари читается как аспирация. Поэтому каждое утверждение саммари должно иметь подтверждающий факт в буллитах — воркер это проверяет (§10.10).
3. **Строка фактов** сразу под саммари: право на работу («EU work authorization — no sponsorship required», если применимо для страны места), готовность к релокации, языки по CEFR, ссылка на LinkedIn. Одна строка, которая снимает жёсткие сомнения до того, как их успели сформулировать. Заполняется только из структурированных полей профиля.
4. **Ключевые компетенции** — 6–10 терминов языком вакансии, каждый подтверждён хотя бы одним фактом. Слова «leadership», «лидерство» и аналоги здесь запрещены: лидерство показывается результатами в буллитах, а не словом в списке.
5. **Опыт по компаниям**, обратная хронология. Для каждой роли: одна строка контекста с масштабом (команда, менеджеры в подчинении, бюджет или P&L, география, охват), затем 2–4 буллита. Первые 3–4 буллита первой страницы — самые сильные под ожидания с весом `must`. Формула буллита: действие → как → измеримый итог; цель — большинство буллитов с числом, буллиты без числа не идут подряд. Мосты `grouped_roles` и `explained_gap` применяются здесь.
6. **Образование и сертификаты.** Регуляторно обязательный сертификат дублируется в строке фактов.

**Даты и перерывы.** Стандарт — месяц и год. При перерыве > 12 месяцев без причины «обучение» модель по умолчанию указывает длительность ролей в годах («3 года») и добавляет короткую причину перерыва отдельной строкой — по данным это заметно повышает отклик; пользователь может вернуть даты одним переключателем.

**Длина.** Опыт 10+ лет — две страницы (рекрутеры предпочитают их одной для таких кандидатов); меньше — одна. Три страницы — только по явному запросу. Роли старше 15 лет — одной строкой.

**Язык и термины.** Язык вакансии; для гипотез — язык по стране компании и настройкам профиля. Точные термины и названия инструментов из `jd_text` попадают в текст только там, где они соответствуют фактам (`analogous_tools` — через явное указание аналога, а не подмену названия).

**Формат по стране.** `format_variant` выбирается по стране места, пользователь может переопределить:

| Вариант | Где применяется | Особенности |
|---|---|---|
| `intl` | международные компании, англоязычные роли, финансы в любой стране | без фото, без даты рождения, семейного положения и гражданства; англо-саксонская структура |
| `uk_ie` | UK, Ирландия | как `intl`; две страницы — норма; личные данные исключены (антидискриминационная практика) |
| `nordic_nl` | Скандинавия, Нидерланды | без фото; допустима короткая строка о личном по желанию пользователя |
| `de_at` | Германия, Австрия, Швейцария | фото часто ожидается — включается при `photo_policy = auto` или `always`; допустимы дата и место рождения по явному согласию |
| `europass` | EU-институты, госсектор, академия, часть Восточной и Южной Европы | структура Europass; в частном секторе топ-компаний проигрывает `intl`, поэтому только по выбору пользователя |

Персональные данные (дата рождения, семейное положение, национальность) не включаются никогда, кроме `de_at` с явным согласием.

**Экспорт.** Ответ структурированный (секции отдельными полями), экспорт в DOCX по умолчанию (парсится ATS надёжнее), PDF — по запросу. Вёрстка: одна колонка, стандартные названия секций, системный шрифт, без таблиц, текстбоксов, иконок, графиков и шкал навыков. Приёмка экспорта — конвертация DOCX в текст сохраняет порядок секций и все буллиты.

**Тон.** Компетентность и теплота одновременно: результаты и масштаб — в буллитах, работа с людьми — тоже фактами («вырастил четырёх менеджеров из специалистов», «удержал команду при реорганизации»), а не прилагательными. Оба измерения по данным предсказывают приглашение; резюме руководителя без второго читается как резюме сильного исполнителя.

### 10.5a Операция Letter

**Вход:** профиль, банк фактов, место, разбор, `tone`, `channel`, `referral_name`.

**Что известно о письмах и как это учтено.** Единственный контролируемый эксперимент даёт таргетированному письму прирост откликов около половины против отсутствия письма, а шаблонному — почти ничего: ценность в кастомизации, а не в факте письма. Письмо чаще читает тот, кто принимает решение, чем рекрутер первичного скрининга. Главный риск 2024–2026 — распознаваемый «сгенерированный» тон: его выявляют не детекторами, а по пустым фразам и отсутствию конкретики, и заметная доля работодателей отсеивает такие заявки. Поэтому письмо в «Периметре» короткое, привязанное к фактам компании и кандидата и всегда проходит проверки §10.10 до показа пользователю; версия, не прошедшая swap-тест, пользователю не показывается.

**Две ветки — две длины.**

- `vacancy` → сопроводительное письмо: 250–350 слов, не больше страницы. Читается вместе с резюме и не пересказывает его.
- `hypothesis` → холодное первое письмо руководителю: 120–180 слов. Это письмо в ящик занятого человека: одно наблюдение, одно доказательство, одна просьба.

(Версия 1.0 задавала 150–200 слов для обеих веток. Сопроводительное расширено, потому что в него должны уместиться мост для гэпа и ответ на возражение; холодное укорочено, потому что его читают с телефона.)

**Сопроводительное письмо — пять блоков, порядок фиксирован.**

1. **Крючок с конкретикой компании.** Одно-два предложения, привязывающие письмо к сигналу или задаче из вакансии и сразу дающие релевантный факт кандидата с числом. Запрещённые начала: «I am writing to express my interest», «Меня заинтересовала ваша вакансия», «Jag söker härmed tjänsten».
2. **Доказательство релевантности.** 2–3 достижения из банка фактов под ожидания веса `must`, каждое с числом; формулировки отличаются от резюме, числа — совпадают.
3. **Мост.** Прямое закрытие главного мягкого гэпа по типу `bridge` из разбора — один абзац, без оправданий и без слова «однако» в начале. Если мягких гэпов нет — абзац о масштабе или траектории.
4. **Почему эта компания и почему сейчас.** Строится из `signal` и `jd_text`; сюда встраивается ответ на главное возражение (`objection.answer`). Этот абзац должен ломаться при замене компании — на нём держится swap-тест.
5. **Спокойный клоуз.** Одна конкретная просьба (разговор на 20 минут на такой-то неделе), без «thrilled», «excited» и «looking forward to the opportunity».

**Холодное письмо (`hypothesis`).** Наблюдение о компании, видимое снаружи, с датой сигнала → проблема, которую такое событие обычно порождает, и факт кандидата с числом, доказывающий, что он такую проблему решал → предложение короткого разговора; роль может быть названа как ещё не существующая. В конце — откуда взят контакт и как отказаться от дальнейших писем (§15.2). Пересказ резюме, список компетенций, вложения — запрещены.

**Параметры.** `tone` регулирует баланс компетентности и теплоты в формулировках, не длину и не структуру: `direct` — короче предложения, больше чисел; `warm` — больше о команде и людях; `neutral` — по умолчанию. `channel = referral | warm` → первое предложение называет того, кто представил (`referral_name`); это самый сильный из доступных сигналов внешней валидации, и он ставится раньше любого достижения.

**Общие запреты.** Фразы из стоп-листа (Приложение Б); факты о компании, которых нет в `signal` / `jd_text`; утверждения о кандидате вне банка фактов; расхождение с резюме по числам и датам; упоминание жёсткого блокера — при неснятом блокере модель получает инструкцию не касаться его, а интерфейс показывает пользователю предупреждение, что письмо его не закроет.

**Ответ:** `subject`, `body`, `word_count`, `bridge_used`, `facts_used`. Тема письма — конкретная и короткая (роль или наблюдение + имя), без «Application for».

### 10.6 Правило контактов

Приложение **не генерирует** email-адреса. Допустимые источники адреса:
1. Адрес опубликован на сайте компании или в вакансии — тогда он сохраняется с полем `source_url`.
2. Пользователь ввёл его вручную.

Любой адрес, пришедший от модели и не подтверждённый пунктом 1, обнуляется. В интерфейсе вместо адреса показывается подсказка, где его искать, и ссылка на поиск по LinkedIn. Причина: правдоподобный несуществующий адрес хуже пустого поля — он расходует попытку и создаёт ложное ощущение работы.

Имя и должность руководителя сохраняются только вместе с `source_url`.

### 10.7 Импорт резюме из файла

- TXT/MD — читается напрямую.
- DOCX — распаковка ZIP и извлечение текста из `word/document.xml` в воркере (без внешних библиотек).
- PDF — файл передаётся в OpenAI как file input, модель `gpt-5.6-luna` возвращает чистый текст. Размер до 10 МБ, до 20 страниц.
- Результат показывается пользователю **для правки перед сохранением** — автоматическое извлечение из PDF ошибается на колонках и таблицах.

### 10.8 Операция Ingest (ручной ввод вакансии)

**Вход:** либо URL, либо текст, вставленный пользователем.

**Шаг 1. Получение текста (только для URL).** Воркер делает GET с честным User-Agent приложения, таймаутом 10 секунд и лимитом 2 МБ, следует не более чем за 3 редиректами. HTML очищается от `script`, `style`, `nav`, `footer`, из остального берётся текст. Если страница отдала < 400 значимых символов, вернула 401/403/429 или прислала страницу с проверкой на бота — операция завершается кодом `jd_fetch_blocked`, и интерфейс просит вставить текст руками.

Так ведут себя большинство крупных площадок: LinkedIn, Indeed и часть корпоративных ATS отдают контент только авторизованным браузерам. Обход этой защиты не предусмотрен — ни headless-браузером, ни сторонними прокси-сервисами. Ветка со вставкой текста поэтому не запасная, а равноправная, и в интерфейсе оба поля показываются рядом.

**Шаг 2. Извлечение структуры.** Модель `gpt-5.6-luna`, Structured Outputs:

```json
{
  "company": "string",
  "role_title": "string",
  "city": "string",
  "country": "string",
  "industry": "string",
  "size": "string",
  "language": "string",
  "seniority": "string",
  "requirements": ["string"],
  "responsibilities": ["string"],
  "contact_email": "string",
  "salary": "string",
  "posted_date": "string",
  "confidence": "high | medium | low",
  "is_job_posting": true
}
```

**Правила:**
- Пустая строка вместо догадки — незаполненное поле лучше выдуманного.
- `is_job_posting = false` (пользователь вставил не вакансию, а, например, страницу «О компании») → интерфейс сообщает об этом и предлагает всё равно создать гипотезу.
- `contact_email` заполняется, только если адрес буквально присутствует в тексте вакансии; правило §10.6 действует и здесь.
- `confidence != high` → распознанное показывается с предупреждением и подсвеченными пустыми полями.
- Полный текст вакансии сохраняется в `jd_text` целиком: он нужен разбору, а не только извлечённая структура.

**Шаг 3. Подтверждение.** Пользователь видит форму с распознанными полями, правит, подтверждает. Без подтверждения место не создаётся — автоматическое сохранение распознанного приводит к базе, засорённой кривыми названиями компаний.

**Дедупликация:** по `company_key` + роль, как в §7. Если совпадение с существующим местом найдено — предлагаем не создавать дубль, а дополнить существующее место текстом вакансии (частый случай: гипотеза, по которой позже открылась вакансия; такое место меняет `kind` с `hypothesis` на `vacancy` с сохранением истории).

**Стоимость:** порядка $0.005 за вакансию.

### 10.9 Бюджет и лимиты

Оценка стоимости при текущих ценах:

| Операция | Порядок стоимости |
|---|---|
| Прогон поиска (6–10 мест, ~6 веб-запросов) | $0.10–0.20 |
| Ручной ввод вакансии (ссылка или текст) | $0.005 |
| Аудит профиля (разово, повтор после правок) | $0.05–0.10 |
| Разбор одного места | $0.02–0.04 |
| Резюме | $0.01–0.02 |
| Письмо | $0.01 |
| Проверки документа (swap-тест) | $0.003 |
| **Активный месяц поиска** (20 прогонов, 80 разборов, 40 писем) | **$5–9** |

Ограничители в воркере: месячный лимит по `usage_log` на пользователя (по умолчанию $15, настраивается), мягкое предупреждение на 80%, жёсткая остановка на 100% с понятным сообщением. Дополнительно — spend limit на стороне OpenAI как последний рубеж.

**[1.2 · Twin]** Такой ограничитель есть в Help_me_clean (`js/limits-core.js`), и из него переносятся три решения.

- **Лимит — чистый модуль, а не условие внутри маршрута.** `limits-core.js` не знает ни про Firebase, ни про HTTP: на вход счётчики и событие, на выход решение. Поэтому он покрыт тестами и пороги в нём — параметры, а не литералы. Для «Периметра» это `budget-core.ts` над `usage_log`: `check(userId, operation) → {allow, spent, limit, level: 'ok'|'warn'|'stop'}`.
- **Отказ возвращает причину, а не только код.** `awardRound()` отдаёт `{awarded, reason, count, limit}`, и клиент по `reason` показывает человеческий текст. §16 требует «понятного сообщения» на превышение бюджета — источником текста должен быть `reason`, а не разбор строки ошибки на фронте. Тело ответа 429: `{error: {code: 'budget_exceeded', spent, limit, resets_at}}` — этого хватает, чтобы экран расходов (§13.1, экран 5) нарисовался без дополнительного запроса.
- **Ограничение убирает награду, но не запрещает действие.** В Help_me_clean третья уборка одной комнаты за день не приносит искорок, но выполнить её никто не мешает — и об этом говорится **заранее**, а не сюрпризом в конце. Здесь ТЗ уже держит это правило («остальное работает», §16), и его стоит усилить: предупреждение на 80% должно называть, **сколько операций осталось** в понятных единицах («хватит примерно на 12 разборов или 30 писем»), а не показывать проценты. Расчёт — по средним из таблицы стоимости выше.

### 10.10 Проверки документов

Каждый сгенерированный документ проходит проверки в воркере до показа пользователю. Дешёвые правила — кодом; одна семантическая проверка — моделью `gpt-5.6-luna`. Результат сохраняется в `documents.checks` и показывается рядом с текстом списком замечаний с уровнем `block` / `warn` / `info`. После правки пользователем проверки перезапускаются автоматически; `block` не запрещает пользователю сохранить и отправить свой текст — он запрещает показывать такой текст как результат генерации.

**Правила (код):**

| Проверка | Документ | Правило | Уровень |
|---|---|---|---|
| Стоп-лист | оба | вхождение фразы из Приложения Б (EN/RU/SV, нормализованно, с учётом словоформ) | `warn`; ≥ 3 вхождений → `block` |
| Квантификация | resume | доля буллитов с числом ≥ 60%; ≥ 2 на роль последних 10 лет | `warn` |
| Верхняя треть | resume | первые 3 буллита закрывают ожидания с весом `must` (по `facts_used` ↔ `fact_id` разбора) | `warn` |
| Саммари подтверждено | resume | каждое утверждение саммари сопоставлено с фактом в буллитах (модель размечает соответствие в структурированном ответе) | `warn` |
| Строка фактов | resume | право на работу, CEFR, релокация присутствуют, если заполнены в профиле и релевантны стране места | `info` |
| Длина | оба | resume: ≤ 2 страницы по оценке знаков на страницу; letter: 250–350 / 120–180 слов по ветке | `warn` |
| Согласованность чисел | letter ↔ resume | все числа письма встречаются в резюме под это место или в банке фактов | `block` |
| Единственный источник | оба | все `facts_used` существуют и `confirmed = 1` | `block` |
| Факты о компании | letter | именованные сущности, даты и числа о компании присутствуют в `signal` / `jd_text` | `block` |
| Одна просьба | letter | ровно одно вопросительное или побудительное предложение в последнем абзаце | `info` |
| Запрещённые начала | letter | первое предложение не из списка шаблонных открытий | `warn` |
| Блокер не упомянут | letter | при неснятом блокере текст не содержит ключевых слов блокера (спонсорство, виза, язык и т. д.) | `warn` |
| Орфография | оба | проверка словарём языка документа | `warn` |

**Семантическая проверка (модель): swap-тест.** Письмо передаётся модели с заменёнными названием компании, ролью и именем адресата на вымышленные, с вопросом: «какие предложения перестали иметь смысл или стали ложными?». Если таких предложений меньше двух — письмо шаблонное: `block`, документ перегенерируется один раз автоматически с результатом теста в промпте; если и вторая версия не проходит — показывается с пометкой и объяснением. Второй вопрос того же вызова: «какие фразы выглядят как написанные без знания компании или как сгенерированные?» — результат `info`, подсвечивается в тексте.

**Что не проверяется намеренно.** Плотность ключевых слов «под ATS» сверх языка вакансии (§1.3) и «AI-детекция» формальными инструментами — они ненадёжны, а рекрутеры ими не пользуются; проверяется то, по чему шаблонность распознаёт человек: пустота и отсутствие конкретики.

**Стоимость:** правила — бесплатно, swap-тест ~$0.003 за документ.

**[1.2 · Twin] Тринадцать правил из таблицы — это чистый модуль, и он должен быть покрыт тестами первым.** В twin-things и Help_me_clean принят и выдержан приём: вся детерминированная логика лежит в модулях `*-core.js`, не импортирующих ни Firebase, ни DOM, ни сеть, и покрыта тестами на `node --test` **без единой внешней зависимости** (`"test": "node --test tests/*.test.mjs"` — весь инструментарий). Сейчас это 45 тестов в twin-things и 157 в Help_me_clean; они гоняются за секунду и ловят регрессии в логике наград, лимитов, санитайзеров и таксономии — то есть ровно там, где ошибка не видна глазом.

В «Периметре» чистой логики существенно больше, чем в любом из трёх приложений, и вся она — на критическом пути ценности продукта:

| Модуль | Что внутри | Какие критерии приёмки закрывает |
|---|---|---|
| `score-core` | формула `100 × Σ(w·s) / Σ w`, веса `must`/`important`/`nice`, правило «блокер не обнуляет score» (§10.4) | 5, 5b |
| `blockers-core` | таблица четырёх измерений §10.4: отношения масштаба (≤2 мягкий, ≥3 жёсткий), CEFR-сравнение, `work_auth` по регионам, прогрессия и средний срок в роли; снятие блокера структурированным полем **без вызова модели** | **5b целиком** — это чистая функция, и критерий формулируется как unit-тест |
| `dedup-core` | `company_key` (регистр, юрформы AB/AS/GmbH/Ltd/Inc/ООО, пунктуация) + расстояние Левенштейна по роли < 0.2 (§7, §10.8) | 7 |
| `checks-core` | все 13 кодовых правил §10.10: стоп-лист со словоформами, доля буллитов с числом, длины по веткам, согласованность чисел «письмо ↔ резюме», «одна просьба», запрещённые начала | **6c, 6d** |
| `audit-core` | метрики чек-листа §10.4a: доля квантифицированных фактов, покрытие ролей, перерывы > 6 мес., средний срок, полнота структурированных полей | 5a (метрическая часть) |
| `budget-core` | §10.9 | — |
| `sanitize-core` | приведение ответов модели к закрытым спискам (`gap_class`, `bridge`, `kind` блокера, `format_variant`) | 5 |

Ни один из этих модулей не требует ни OpenAI, ни D1, ни Google — значит, **все они пишутся и тестируются на Этапе 0**, до того как заработает первая интеграция, и дальше не ломаются молча. Практическая выгода конкретна: критерии 5b, 6c и 6d в §18 сейчас сформулированы как ручная проверка на живых данных; будучи чистыми функциями, они превращаются в тесты, которые гоняются на каждом коммите. Поскольку и воркер, и фронтенд здесь на TypeScript, ядро можно держать одной папкой `core/`, импортируемой обоими — в семействе Twin такой возможности не было (браузер и воркер на разных языках), и это преимущество «Периметра» стоит использовать: счётчик слов в письме на экране и проверка длины в воркере обязаны быть одной функцией, иначе они разойдутся.

## 11. Интеграция с Google Sheets

### 11.1 Создание таблицы

При первом обращении к `/api/sheet/ensure` воркер создаёт таблицу через Drive API (`files.create`, mimeType `application/vnd.google-apps.spreadsheet`), имя «Периметр — поиск работы». `spreadsheet_id` пишется в `users`. Файл принадлежит пользователю, лежит на его диске, живёт после удаления приложения. Scope `drive.file` даёт приложению доступ только к этому файлу.

Если пользователь удалил таблицу — при следующей синхронизации Drive вернёт 404, приложение создаёт новую и сообщает об этом.

| T | Обновлено | приложение |

Колонки Q2, Q3, R и S — зона пользователя, приложение их не перезаписывает (§11.4).

**Лист «Ожидания»** — по строке на каждое ожидание: ID места, компания, ожидание, вес, чем закрыто, сила, класс разрыва, тип моста. Даёт возможность строить сводные таблицы — в том числе увидеть, какой гэп повторяется по многим местам и стоит закрыть в самом профиле, а не в каждом письме.

**Лист «Документы»** — ID места, тип, тема, текст, версия, дата.

### 11.3 Синхронизация БД → лист

- Триггер: завершение прогона, изменение разбора, генерация документа, ручной запрос.
- Метод: `spreadsheets.values.batchUpdate` пачками, не построчно.
- Новые места добавляются в конец, `sheet_row` сохраняется в БД.
- Обновление существующих — по `sheet_row`, с проверкой, что в колонке A стоит ожидаемый ID (защита от сдвига после ручной вставки строк). При расхождении — полный ресинк листа.
- Форматирование при создании: закреплённая шапка, автофильтр, ширины колонок, условное форматирование колонки K (зелёный ≥ 70, жёлтый 40–69, серый < 40), красная заливка непустых ячеек L2, выпадающие списки в колонках Q2 и R.

### 11.4 Синхронизация лист → БД

Двусторонняя синхронизация ограничена намеренно: пользователь редактирует только статус (R), комментарий (S), канал и представляющего (Q2–Q3) и контакты (N–Q).

- Триггер: открытие приложения (не чаще раза в 5 минут), явная кнопка «Подтянуть из таблицы».
- Чтение диапазона `Места!A:T`, сопоставление по ID из колонки A.
- Конфликт разрешается по времени: если `updated_at` в БД новее отметки в колонке T, побеждает БД, пользователю показывается уведомление о расхождении.
- Строки, добавленные пользователем вручную (пустая колонка A), импортируются как новые места со статусом `new` и типом `hypothesis`.

### 11.5 Отказоустойчивость

Google API может отдать 429 или 503. Синхронизация не блокирует пользовательский сценарий: при ошибке место всё равно сохраняется в БД, в интерфейсе появляется неблокирующее уведомление «в таблицу пока не записано», и задача попадает в очередь на повтор (экспоненциальная задержка, до 5 попыток). Расхождение БД и таблицы — штатная ситуация, а не ошибка.

**[1.2 · Twin]** Это тот же приём, что в twin называется fire-and-forget: сводка по тегу пересчитывается после каждого сохранения задачи фоновым вызовом, и пользователь её никогда не ждёт. Правило семейства сформулировано в `CLAUDE.md` одной строкой: «сводки по тегам — fire-and-forget, никогда не блокировать на них интерфейс». Здесь стоит добавить оговорку из §4.3.2: у twin такой фоновый шаг **молча пропускается**, если ключ не задан, и пользователь считает, что всё работает. Поэтому неблокирующее уведомление «в таблицу пока не записано» должно быть **липким до успеха**, а не всплывающим на пять секунд, и §11.4 должен уметь показать возраст последней удачной синхронизации.

Ограничение «не чаще раза в 5 минут» на pull — тот же паттерн, что `localStorage('monthlyGenerated')` в twin (ключ-отметка, гасящая повторный дорогой прогон в том же периоде). Отметку держать на сервере, а не в браузере: у одного пользователя два устройства, и клиентская отметка даст двойной pull.

## 12. Отправка писем

### 12.1 MVP

Кнопки «Скопировать текст» и «Открыть в почте» (`mailto:` с подставленными темой и телом). Отправка руками, из своего почтового клиента.

### 12.2 v2, вариант А (рекомендуемый)

Scope `gmail.compose`, создание **черновика** в Gmail пользователя через `users.drafts.create`. Пользователь открывает черновик, проверяет и отправляет сам. Это оставляет человека в контуре принятия решения и снижает риск испорченного первого впечатления.

### 12.3 v2, вариант Б

Scope `gmail.send`, отправка прямо из интерфейса. Требует полной верификации Google и CASA-аудита. Оправдан только если продукт выходит за рамки персонального инструмента.

### 12.4 Ограничения по существу

Независимо от варианта: не более 10 писем в сутки, обязательный предпросмотр каждого письма, запрет отправки одного текста нескольким адресатам одним действием. Холодное обращение к руководителю работает как персональное письмо; как рассылка оно не работает и вредит репутации кандидата. Плюс требования GDPR к обработке контактных данных (§15.2).

**Канал прежде текста.** Для middle+ ролей referral — структурно другой канал: доля таких заявок мала, но они дают непропорционально большую долю наймов, а конверсия в интервью на порядок выше холодной подачи (точные множители расходятся между источниками, направление эффекта устойчиво; Приложение В). Поэтому перед первой отправкой по месту интерфейс задаёт один вопрос — «Есть ли кто-то, кто может вас представить в этой компании?» — и предлагает заполнить `channel` и `referral_name`; при `referral` письмо генерируется заново с упоминанием представляющего. Приложение не ищет знакомых за пользователя (§1.3), но делает выбор канала осознанным шагом, а не пропущенным по умолчанию.

## 13. Фронтенд

### 13.1 Экраны

**1. Вход.** Одна кнопка, короткое объяснение, какие доступы запрашиваются и зачем.

**2. Профиль.** Резюме (текст + импорт файла), свободные сведения, периметр ролей, отрасли, исключения, география, охват. Структурированный блок «Что снимает сомнения»: масштаб управления (команда, менеджеры, бюджет/P&L, география), право на работу по регионам, языки с выбором уровня CEFR, готовность к релокации, перерывы и их причины, LinkedIn с чек-листом комплексности, политика фото. Автосохранение с задержкой 700 мс. Под резюме — панель аудита (§10.4a): метрики в виде компактных индикаторов (доля фактов с числом, масштаб, прогрессия, перерывы, языки, право на работу, LinkedIn) и список правок по убыванию эффекта; банк фактов — редактируемый список с чекбоксом подтверждения и подсветкой фактов без числа. Индикатор заполненности: пока резюме пустое, кнопка поиска неактивна с объяснением; пока аудит не пройден, кнопка активна, но индикатор жёлтый с подсказкой, что документы будут слабее.

**3. Места.** Кнопка «Добавить вакансию» рядом с «Найти места»: одно поле для ссылки, одно для текста, работает любое из двух. После распознавания — форма подтверждения с подсвеченными пустыми полями. Список слева (компания, роль, метка типа, совпадение, статус), карточка справа. На узких экранах — две страницы с переходом «назад к списку».

**4. Карточка места.**
- Шапка: компания, отрасль, город, размер, метка «вакансия / гипотеза», ссылка на источник.
- Сигнал.
- Блокеры — если есть, первым блоком после сигнала, красным: вид блокера, в чём именно, кнопки «снять уточнением профиля» (ведёт в нужное поле) и «в архив».
- Разбор: шкала закрытия ожиданий, парный список «ждут / есть у вас» с весом и пометкой силы; мягкие гэпы отдельной группой с типом моста и фразой `gap_answer`; пометка «реконструкция», если разбор без текста вакансии.
- УЦП и главное возражение (риск нанимающего → чем снимается).
- Контакты; канал и тот, кто может представить.
- Резюме под место (редактируемое, версии): выбор формата страны и числа страниц, визуальная отбивка верхней трети, замечания проверок §10.10 рядом с текстом с переходом к строке.
- Письмо (редактируемое, тема отдельно): счётчик слов с целевым диапазоном, результат swap-теста, подсветка фраз стоп-листа и фраз, помеченных как шаблонные.
- Управление статусом, архивирование.

**5. Расходы.** Потрачено за месяц, лимит, разбивка по операциям.

### 13.2 Состояния интерфейса

Для каждого асинхронного действия обязательны четыре состояния: покой, ожидание (с текстом этапа и счётчиком секунд), успех (что именно получилось), ошибка (что произошло и что делать). Глобальный статус-бар под шапкой, видимый на всех экранах, — единая точка для сообщений; дублирование сообщений внутри панелей не допускается.

Долгие операции запрещено оставлять без обратной связи дольше 400 мс. Прогон поиска идёт 1–3 минуты — этапы должны меняться, иначе пользователь считает, что приложение зависло.

**[1.2 · Twin]** Четвёртое состояние — «ошибка» — в семействе проседает чаще всего, и не из-за спешки, а потому что тихий отказ выглядит как отсутствие проблемы. Конкретный случай задокументирован в twin: фоновая сводка по тегу пропускается без ключа OpenAI, ничего не показывается, фича считается рабочей (§4.3.2). Отсюда два жёстких требования, которых в 1.1 нет прямо:

- **Ни один AI-вызов не завершается тихо.** Даже фоновый и даже успешный-но-деградировавший: `degraded: true` (§10.1) обязан быть виден на карточке места, иначе пользователь не поймёт, почему разбор стал хуже.
- **Неудачные вызовы пишутся в `usage_log`** (§7) со стоимостью и причиной. Иначе экран расходов (§13.1, экран 5) будет одинаково показывать «$0» и когда всё дёшево, и когда ничего не работает.

Готовая форма для «ожидания» — список этапов из twin (`task.html`, `aiDraft()`): шаги объявлены массивом, нарисованы заранее все сразу, пройденные помечаются галочкой. Пользователь видит не только что идёт работа, но и сколько её осталось.

### 13.3 Требования к вёрстке

- Мобильные экраны: страница прокручивается обычным образом, фиксированная высота `100vh` не используется — при появлении клавиатуры она ломает доступ к элементам. Шапка липкая.
- Все интерактивные элементы — не менее 44×44 px.
- Контраст текста к фону не ниже 4.5:1; состояние `disabled` должно быть визуально отличимо и читаемо.
- Клавиатурная навигация и видимый фокус.
- Тексты интерфейса — русский; тексты документов — на языке места.

### 13.4 Что берётся готовым

**[1.2 · Twin]** Требования §13.3 — не гипотеза: они выведены и выполнены в трёх приложениях семейства, которыми пользуются с телефонов. Переносится следующее.

- **Дизайн-система на CSS-переменных.** Палитра, типографика, радиусы и тени — один набор переменных в `:root`; тема или бренд — это подмена значений, а не правка компонентов (в Help_me_clean на этом сделаны пользовательские темы: семья задаёт двенадцать цветов, интерфейс перекрашивается целиком). Для React/TS переносятся сами переменные и правило «компонент не знает цвета, он знает роль цвета».
- **Правила мобильной вёрстки, уже оплаченные болью:** отказ от `height: 100vh` (клавиатура на iOS ломает доступ к нижним элементам — это в §13.3 и попало из практики), липкая шапка, цели 44×44, ширина 375 px как рабочий минимум. Стоит взять и чек-лист: три приложения проверены на iOS Safari и Android Chrome.
- **Голосовой ввод (twin → `voice.js`).** Web Speech API, без ключа и без сервера: `attachVoiceBtn(el)` навешивает кнопку 🎤 на любой `input`/`textarea`, отдельная кнопка переключает язык распознавания EN/RU, выбор хранится локально. В «Периметре» два места, где это заметно меняет опыт: **свободные сведения об опыте** (§13.1, экран 2 — самая ценная и самая нелюбимая часть заполнения; §3.1 честно называет её работой на 15–30 минут, и надиктовать её проще, чем написать) и **комментарий к месту** (`user_note`). Файл — не ES-модуль (IIFE с глобалами на `window`), поэтому переносится код распознавания, а не файл; шведский добавляется одной строкой в карту языков.
- **PWA-оболочка** (`pwa.js` / `sw.js` / `manifest.json`) — установка на домашний экран и офлайн-оболочка. Дёшево, ставится в конце Этапа 0 и сразу делает приложение похожим на приложение на телефоне, где §14 требует < 2 с до интерактивности на 4G.

**Открытый вопрос 1 (многоязычный интерфейс) — см. ответ в §19: он уже решён в Help_me_clean, и решение переносится.**

## 15. Безопасность и приватность

### 15.1 Общее

- Секреты только в воркере (§6), ключ OpenAI не покидает сервер ни при каких условиях.
- Все запросы к `/api/*` требуют валидной сессии, кроме `/api/auth/*`.
- Изоляция данных: каждый SQL-запрос содержит `user_id` из сессии; параметр `user_id` из клиента не принимается никогда.
- Rate limiting на уровне воркера: 60 запросов/мин на сессию, отдельные лимиты на AI-операции.
- Заголовки: CSP без `unsafe-inline`, HSTS, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`.
- Зависимости фронта минимальны, автообновление через Dependabot.

### 15.2 Персональные данные

Резюме — персональные данные, пользователь находится в ЕС, применяется GDPR.

- **Свои данные.** Основание — согласие при регистрации. Хранятся в D1 (регион EU), передаются в OpenAI при генерации с `store: false`.
- **Данные третьих лиц** (имя и должность руководителя компании). Обрабатываются по законному интересу в контексте профессиональной коммуникации B2B. Требования: хранить минимум (имя, должность, публичный корпоративный контакт), не хранить личные адреса и телефоны, в первом письме указывать источник контакта и способ отказаться от дальнейших обращений, удалять контакт по первому требованию. Регистр обработки ведётся в документации проекта.
- **Политика конфиденциальности** обязательна для верификации Google, содержит перечень scopes и назначение каждого.

### 15.3 Удаление аккаунта

`POST /api/account/delete`: каскадное удаление всех строк пользователя, удаление сессий, отзыв refresh-токена через `https://oauth2.google.com/revoke`. Google-таблица **не удаляется** — она принадлежит пользователю; интерфейс явно об этом сообщает и даёт ссылку.

## 16. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| OpenAI 429 | 3 повтора с задержкой 2/8/20 с, затем модель ступенью ниже, затем понятная ошибка |
| OpenAI вернул невалидный JSON | 1 повтор с уточнением схемы; при повторе — ошибка, сырой ответ в лог без персональных данных |
| Веб-поиск ничего не нашёл | Прогон завершается успешно с `added = 0` и текстом «по этим настройкам ничего не нашлось, попробуйте расширить охват» |
| Токен Google протух | Обновление через refresh; при `invalid_grant` — баннер повторного входа |
| Sheets 429/503 | Очередь повтора, неблокирующее уведомление (§11.5) |
| Превышен месячный бюджет | Блокировка AI-операций, экран расходов, остальное работает |
| Прогон завис > 5 мин | `failed`, кнопка «Повторить», кнопки интерфейса разблокированы |

Общее правило: ни одна ошибка не оставляет интерфейс в состоянии, где кнопки заблокированы навсегда. Любое `busy` снимается по таймауту.

## 17. Этапы

**Этап 0. Каркас (1 неделя).** Репозиторий, Pages + Worker на одном домене, D1 со схемой, Google OAuth, сессии, экран профиля с сохранением. Критерий: вход и сохранение профиля работают на телефоне.

**Этап 1. Ядро (2,5 недели).** Ingest (ручной ввод по ссылке и тексту) — делается первым, он даёт рабочий продукт без зависимости от качества поиска. Сразу за ним — структурированные поля профиля, Profile Audit и банк фактов (§10.4a): они нужны и разбору, и документам. Затем Discover через очередь со статус-баром, Analyse с валидацией фактов, правилами блокеров и типами мостов, список и карточка места с блоком блокеров, дедуп, лимиты расходов. Критерий: вставленная ссылка на вакансию доходит до разбора ожиданий с классификацией разрывов; из пустого профиля до разобранного места нет ручных действий в БД.

**Этап 2. Документы (1,5 недели).** Resume с форматами по странам, Letter двух веток, проверки §10.10 со swap-тестом, версии, правка руками, канал и представляющий, `mailto`. Критерий: письмо можно отправить из своего почтовика за два клика; ни одно сгенерированное письмо не показывается без результата swap-теста.

**Этап 3. Таблица (1 неделя).** Создание таблицы, полная синхронизация в обе стороны, форматирование, CSV. Критерий: правка статуса в таблице видна в приложении.

**Этап 4. Экспорт и почта (1–2 недели).** DOCX и PDF резюме и письма, Gmail-черновики, экран расходов, удаление аккаунта, политика конфиденциальности.

**Этап 5 (опционально).** Отслеживание откликов, напоминания о follow-up, сравнение мест между собой, дайджест новых мест на почту. Аналитика по каналам с порогами, меняющими стратегию: отклик на холодные заявки < 3–5% при 15+ отправках → приложение предлагает сместить усилия на тёплые контакты; приглашают на интервью, но не дальше → приложение прямо говорит, что документы оптимизировать больше не нужно, проблема на другом этапе.

**[1.2 · Twin] Правки к плану этапов.**

- **Этап 0 сокращается за счёт переноса.** PWA-оболочка, дизайн-система, правила вёрстки и голосовой ввод (§13.4) не проектируются, а переносятся — это часы, а не дни. Освободившееся время уходит на две вещи, которые в 1.1 не выделены отдельно: **механизм миграций D1** (§4.3.4 — заводится, пока таблиц семь) и **чистое ядро** (§10.10): `score-core`, `blockers-core`, `dedup-core`, `checks-core`, `audit-core`, `budget-core`, `sanitize-core` с тестами. Ни один из них не требует OpenAI, Google или живой БД, поэтому пишутся первыми и дальше не переписываются. Критерий Этапа 0 дополняется: `npm test` зелёный, критерий 5b выполняется как unit-тест ещё до того, как заработал первый вызов модели.
- **Экран конфига — в Этап 1, не в пятый** (§10.1). Иначе §19 «ревизия порогов по итогам первых двух недель» и Приложение Б «список пополняется по замечаниям пользователей» останутся декларациями: каждое изменение потребует передеплоя, и потому не случится.
- **Параллельность прогона поиска — в Этап 1 сразу** (§4.3.3, §9.1). Переделывать последовательный цикл в пул после того, как он оброс обработкой ошибок и частичными результатами, дороже, чем написать пул сразу.
- **Этап 2 удешевляется:** экран подтверждения фактов (§10.4a) и подтверждения распознанной вакансии (§3.4) — один и тот же компонент «черновики с чекбоксами», написанный дважды в семействе (§10.4a). Планировать как одну работу, а не две.

## 18. Критерии приёмки

1. Ключ OpenAI отсутствует в бандле фронтенда и в сетевых запросах браузера (проверяется поиском по бандлу и вкладкой Network).
2. Вход через Google работает на iOS Safari и Android Chrome; сессия переживает перезагрузку страницы и закрытие браузера.
3. Профиль сохраняется без потерь при вводе текста длиной 20 000 символов.
4. Прогон поиска на профиле VP Product / логистика возвращает не менее 6 мест, из них не менее 3 гипотез, каждая с рабочей ссылкой на источник и датой сигнала не старше 12 месяцев.
5. В разборе — от 5 до 7 ожиданий с весом, у каждого `evidence` подтверждается текстом профиля или фактом из банка либо помечен как разрыв с классом `hard` / `soft`; у каждого мягкого гэпа указан тип моста.
5a. Аудит профиля на трёх реальных резюме руководителей извлекает не менее 90% достижений с числами (ручная сверка) и ни одного факта без подтверждённого `source_hint`; каждая рекомендация аудита указывает на конкретную роль или факт.
5b. Разбор вакансии с требованием свободного немецкого при отсутствии немецкого в профиле выдаёт блокер `language`; после добавления «German — C1» блокер снимается без нового вызова модели, `score` не меняется. Аналогично для права на работу и масштаба.
6. Ни одно место не содержит email-адреса, не подтверждённого источником.
6c. Сгенерированное резюме: саммари ≤ 3 строк и каждое его утверждение сопоставлено с буллитом; ≥ 60% буллитов содержат число; первые три буллита закрывают ожидания `must`; строка фактов присутствует; в списке компетенций нет слов из стоп-листа; DOCX открывается в Word и LibreOffice, конвертация в текст сохраняет порядок секций и все буллиты; при `format_variant = intl` в документе нет фото и персональных данных.
6d. Сгенерированное письмо: длина в диапазоне ветки; swap-тест находит ≥ 2 предложения, теряющих смысл при замене компании; нет фраз стоп-листа; все числа письма совпадают с резюме под это место; ровно одна просьба в конце; при `channel = referral` представляющий назван в первом предложении.
6e. Ни одно из 10 проверенных вручную писем не содержит утверждений о компании, отсутствующих в `signal` / `jd_text`, и утверждений о кандидате, отсутствующих в банке фактов.
6a. Ссылка на вакансию с корпоративного сайта и с job-борда доходит до формы подтверждения не дольше 15 секунд; закрытая для ботов страница даёт понятное сообщение с предложением вставить текст, а не пустую форму и не ошибку.
6b. Разбор места, созданного из текста вакансии, содержит только ожидания, присутствующие в этом тексте.
7. Все места и разборы видны в Google-таблице пользователя; изменение статуса в таблице подхватывается приложением.
8. Любая AI-операция, идущая дольше 1 секунды, показывает этап и счётчик времени; после ошибки все кнопки снова активны.
9. На экране 375 px все элементы достижимы, ни один блок не уезжает за границы, контраст соответствует WCAG AA.
10. Удаление аккаунта стирает все данные из D1 и KV и отзывает токен Google.

**[1.2 · Twin] Дополнительные критерии, следующие из переиспользования.**

11. **Ядро тестируется без внешних систем.** `npm test` (или эквивалент) проходит без сети, без ключей и без базы и покрывает `score-core`, `blockers-core`, `dedup-core`, `checks-core`, `audit-core`, `budget-core`, `sanitize-core`. Критерии 5b, 6c и 6d выражены в этих тестах, а не только в ручной проверке. Прогон — быстрее 5 секунд (ориентир семейства: 157 тестов Help_me_clean идут ~1,2 с).
12. **Счётчики на экране и проверки в воркере — одна функция.** Счётчик слов в письме, оценка числа страниц резюме и доля буллитов с числом на фронтенде дают ровно те же значения, что и проверки §10.10 на сервере, потому что импортируют один модуль `core/`. Расхождение считается дефектом, а не округлением.
13. **Ключ OpenAI принадлежит только этому приложению.** Воркер «Периметра» — отдельный деплой с отдельным project-ключом и отдельным spend limit; существующий `task-intake-worker` семейства Twin не используется (§4.3.1). Проверяется тем, что отзыв ключа «Периметра» не ломает twin, twin-things и Help_me_clean, и наоборот.
14. **Ни один AI-вызов не завершается тихо.** Неудачные и деградировавшие вызовы попадают в `usage_log` и видны пользователю: на карточке места — пометка `degraded`, на экране расходов — число неудачных вызовов за месяц (§13.2).

Стоп-лист (Приложение Б) кладётся в тот же языковой словарь, ключом по языку документа, — тогда добавление шведского не трогает код проверок.

## Приложение А. Чек-лист резюме, зашитый в аудит (§10.4a) и проверки (§10.10)

1. **Верхняя треть — сильнейшее.** Заголовок роли + саммари 2–3 строки; заявка в саммари = то, что подтверждают буллиты ниже.
2. **Масштаб явно:** размер команды, число менеджеров в подчинении, бюджет или P&L, география, охват пользователей или клиентов — строкой контекста под каждой руководящей ролью.
3. **Каждый буллит — результат с числом:** действие → как → измеримый итог. Большинство буллитов с метрикой, буллиты без числа не подряд.
4. **Прогрессия видна:** промоушены, рост охвата между ролями.
5. **Язык вакансии:** точные термины и инструменты из описания — только где это правда.
6. **Формат:** одна колонка, стандартные заголовки, DOCX по умолчанию, без таблиц, текстбоксов, графики, шкал навыков.
7. **Длина:** две страницы при 10+ годах опыта; роли старше 15 лет — одной строкой.
8. **Даты и перерывы:** при перерыве — длительность ролей в годах и короткая причина; обучение — лучшая причина.
9. **Строка фактов:** право на работу, готовность к релокации, языки по CEFR, ссылка на LinkedIn.
10. **Фото и персональные данные — по стране:** без фото и без даты рождения для `intl`, `uk_ie`, `nordic_nl`; фото допустимо для `de_at`.
11. **Работа с людьми — фактами,** а не словом «лидерство» в навыках.
12. **Без опечаток:** проверка словарём; рекомендация пользователю прочитать чужими глазами.

## Приложение Б. Стоп-лист фраз (начальная версия, ведётся в конфиге воркера)

Фразы ниже — маркеры пустоты, по которым скринер распознаёт шаблон. Проверка нормализованная, с учётом словоформ; список пополняется по замечаниям пользователей и по результатам вопроса swap-теста о «сгенерированных фразах».

**Английский:** proven track record · results-driven / results-oriented · detail-oriented · team player · dynamic professional · passionate about · thought leader · go-getter · think outside the box · synergy / synergies · seasoned professional · hard-working · self-starter · hit the ground running · I am writing to express my interest · I am thrilled / excited to apply · I believe I would be a great fit · I look forward to the opportunity · responsible for (в буллитах — заменяется глаголом действия) · leverage (без объекта с числом) · strong communication skills · fast-paced environment.

**Русский:** командный игрок · результативный лидер · нацеленность на результат · стрессоустойчивость · коммуникабельность · ответственность и пунктуальность · богатый опыт · проверенный трек-рекорд · меня заинтересовала ваша вакансия · буду рад стать частью команды · обладаю лидерскими качествами · успешно решал задачи (без числа).

## Приложение В. Источники требований 1.1 и их надёжность

Требования §10.4–10.10 опираются на сводку исследований, приложенную к проекту. Для калибровки порогов важно понимать, что в ней надёжно, а что — нет.

**Надёжнее (рецензируемые или контролируемые):** эффект указания длительности ролей в годах при перерывах (полевой аудит на реальных работодателях, *Nature Human Behaviour*, 2023); штраф за частую смену работодателей и его зависимость от функции (аудиты Chicago Booth / U. Zurich, McGill); прирост найма и зарплат при AI-помощи в написании резюме с последующей правкой (RCT NBER, ~480 тыс. соискателей); совместное влияние воспринимаемых «компетентности» и «теплоты» на приглашения (мета-анализ 21 correspondence-study, 2024); доля вакансий на местном языке и требования английского для менеджеров в ЕС (OECD, 2023).

**Направление надёжно, величины — нет (коммерческие полевые эксперименты и опросы вендоров):** +~50% откликов у таргетированного письма против отсутствия письма и почти ноль у шаблонного; предпочтение двух страниц при 10+ годах опыта; штраф за перерыв и его снижение при указании причины; эффект комплексного LinkedIn; «6–7 секунд» первичного просмотра (eye-tracking на 30 рекрутерах); доля компаний с ATS; оценки конверсии referral против холодной подачи (от 4× до 10–20× в разных источниках); доля рекрутеров, отсеивающих «сгенерированные» письма (самоотчёты, при слепых тестах точность распознавания низкая).

**Следствия для ТЗ:** пороги в §10.4a и §10.10 (60% буллитов с числом, ≥ 2 предложения в swap-тесте, диапазоны длины, ×3 / ×10 для масштаба) — продуктовые настройки, а не законы; они вынесены в конфиг и пересматриваются по итогам первых двух недель ручной оценки (§19). Формулировки в интерфейсе избегают точных процентов из вендорских данных: «заметно повышает отклик», а не «+58%».

### Г.3 Честная оценка объёма

Чтобы решение принималось без иллюзий:

- **Прямого кода к переносу — на день-полтора.** Это Origin-проверка, извлечение JSON, генерация id, `fitWithin`, голосовой ввод, PWA-оболочка, переменные дизайн-системы. Всё остальное придётся писать заново под React/TS и D1.
- **Архитектурных решений — на несколько недель сэкономленного времени и, что важнее, на несколько неслучившихся ошибок.** Конфиг с экраном, контракт вызова с санитайзом, чистое ядро с тестами, серверный бюджет с причиной, язык вывода параметром — каждое из них в семействе появилось не сразу, а после того, как отсутствие обошлось дорого.
- **Три предупреждения из §4.3 стоят отдельно от всякой экономии:** не переиспользовать общий воркер, не допускать тихих отказов, не верить документации про параллельность без взгляда в код. Каждое проверено на живой установке.
