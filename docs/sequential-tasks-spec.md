# ТЗ — Управление последовательными задачами (GTD next-action model)

> Статус: черновик к реализации. Не самостоятельная фича, а перестройка того,
> **что именно показывает трекер** и как связаны шаги внутри дела.
> Опорные методики — GTD (David Allen) + модель sequential/parallel из OmniFocus.

-----

## 1. Проблема (три разные боли)

| # | Боль пользователя | Термин GTD | Механизм-решение |
|---|---|---|---|
| A | «Написала ТЗ → возникает *согласовать и поставить в разработку*» | successor / sequential steps | последовательные подзадачи, роллинг «первого доступного» |
| B | «У *ПМЖ в Швеции* уже есть подзадачи: заявление / профсоюз / страховки» | project ≠ action | режим `parallel`, показ доступных действий |
| C | «На трекере висит крупное дело, а текущей/следующей подзадачи не видно» | работаешь по списку **next actions**, не по списку проектов | карточка показывает **первое доступное действие**, не только название проекта |

**Корень:** главный экран (`index.html`) показывает `task.title` (это *проект*),
а не следующее физическое действие. В GTD рабочий список — это next actions, а
проекты живут отдельно (для ревью). Сейчас `nextAction` хранится **только как дата**
(`index.html:579`) — текст следующего шага теряется.

-----

## 2. Ключевые понятия (как мапятся на нашу модель)

- **Проект** — задача (`task`), у которой есть подзадачи. Название проекта — контекст, не действие.
- **Действие (next action)** — подзадача. То, что реально делаешь.
- **Первое доступное действие (first available action)** — вычисляемое, НЕ хранимое:
  - `subtaskMode: "parallel"` → доступны **все** подзадачи со `status ∉ {done, blocked}`;
    «следующая» = самая ранняя по `dueDate`, затем по порядку в массиве.
  - `subtaskMode: "sequential"` → доступна **только первая** подзадача со `status !== 'done'`;
    всё после неё — заблокировано порядком (показываем приглушённо). Если эта первая
    имеет `status === 'blocked'` → доступных нет (дело в ожидании).
- **Waiting For** — подзадача/задача со `status === 'blocked'`. Не мельтешит в
  доступных, но не потеряна: видна в отдельном фильтре «⏳ Waiting». (Статус `blocked`
  уже есть в схеме — сейчас просто не задействован.)
- **Successor / «а что дальше?»** — когда следующий шаг рождается только в момент
  завершения (пример: «прочла письмо из школы → теперь готовлю форму»).

## 3. Изменения схемы (Firestore `tasks/`)

Обратная совместимость обязательна: все поля опциональны, старые задачи валидны.

```js
{
  // ...существующие поля без изменений...

  subtaskMode: "parallel" | "sequential",   // NEW, default "parallel" при отсутствии

  subtasks: [{
    // ...существующие поля...
    // status уже поддерживает "blocked" — используем его как Waiting For
    waitingOn: "string|null"                 // NEW, опц.: кого/что ждём (для blocked)
  }],

  spawnOnDone: {                             // NEW, опц.: successor-задача
    title: "string",
    tags: ["..."],
    primaryTag: "string|null"
  } // | null
}
```

Никаких новых коллекций. `nextAction` (дата) **остаётся** — это «когда работать»,
ортогонально «что делать».

## 4. Общий хелпер (вынести в оба файла или в общий inline-скрипт)

```js
// Возвращает { subtask, index } первого доступного действия, или null.
function firstAvailableSubtask(task) {
  const subs = task.subtasks || [];
  if (!subs.length) return null;
  const mode = task.subtaskMode || 'parallel';

  if (mode === 'sequential') {
    const idx = subs.findIndex(s => s.status !== 'done');
    if (idx === -1) return null;                    // всё сделано
    if (subs[idx].status === 'blocked') return null; // ждём — доступных нет
    return { subtask: subs[idx], index: idx };
  }

  // parallel
  const candidates = subs
    .map((s, i) => ({ s, i }))
    .filter(x => x.s.status !== 'done' && x.s.status !== 'blocked');
  if (!candidates.length) return null;
  candidates.sort((a, b) => {
    const da = a.s.dueDate || '9999-99-99';
    const db = b.s.dueDate || '9999-99-99';
    if (da !== db) return da < db ? -1 : 1;
    return a.i - b.i;
  });
  return { subtask: candidates[0].subtask, index: candidates[0].i };
}

// В sequential-режиме: индексы, заблокированные порядком (после первой не-done).
function orderBlockedIndexes(task) {
  if ((task.subtaskMode || 'parallel') !== 'sequential') return new Set();
  const subs = task.subtasks || [];
  const firstPending = subs.findIndex(s => s.status !== 'done');
  if (firstPending === -1) return new Set();
  const set = new Set();
  for (let i = firstPending + 1; i < subs.length; i++) set.add(i);
  return set;
}
```

## 5. `index.html` — трекер

### 5.1 Карточка показывает следующее действие (боль C)

В `renderCards()` (около `index.html:566`) для задач с подзадачами:

- Вычислить `firstAvailableSubtask(t)`.
- Если есть доступное действие — показать **его текст** отдельной строкой, крупно:
  `→ Заполнить заявление на ПМЖ` + чип срока подзадачи (`dueDate`).
- Название проекта (`t.title`) остаётся, но как **подзаголовок/контекст** (мельче),
  а не как главная строка.
- Если доступных нет, но есть незавершённые подзадачи в статусе `blocked` →
  строка `⏳ Ждём: {waitingOn}` вместо действия.
- Если подзадач нет — поведение как сейчас (действие = сама задача).

Мини-бейдж режима рядом с прогрессом: `⇉ parallel` / `▸ sequential` (при `sequential`).

Существующая строка `nextActionHtml` (`index.html:579`) остаётся как чип «когда»
(`→ Today`), но перестаёт быть единственным носителем «следующего».

### 5.2 Сортировка

В `sortTasks`/`getFiltered` (около `index.html:546`): задачи с доступным действием
и ранним `dueDate` этого действия — выше. Waiting-задачи (нет доступных, есть blocked)
опускаются к низу активного списка.

### 5.3 Новый фильтр «⏳ Waiting»

Добавить таб рядом с существующими (`index.html:259-263`). Показывает задачи, где
есть хотя бы одна подзадача `status === 'blocked'` **или** сама задача `blocked`.
Это GTD-список @Waiting For.

## 6. `task.html` — деталь задачи

### 6.1 Переключатель режима подзадач

В шапке секции Subtasks (около `task.html:222`) — тумблер:
`⇉ Parallel  |  ▸ Sequential`. Пишет `task.subtaskMode`, вызывает `save()` + `renderSubtasks()`.

### 6.2 `renderSubtasks()` (около `task.html:538`)

- Подсветить **первое доступное** действие (рамка/акцент — «делай это»).
- В `sequential`: индексы из `orderBlockedIndexes(task)` показать приглушённо
  с меткой «⏸ ждёт предыдущего».
- Подзадачи `status === 'blocked'` — метка `⏳ Waiting${waitingOn ? ': '+waitingOn : ''}`.

### 6.3 Захват successor при завершении (боль A, случай «рождается в конце»)

При `toggleSubtaskDone` и при `setStatus('done')`:
- Если у задачи есть `spawnOnDone` → создать новую задачу из него (`setDoc` новый id).
- Иначе, если завершение закрыло **последнюю** доступную подзадачу или всю задачу —
  показать лёгкий инлайн-промпт **«Следующее действие?»** с одним полем: заполнила →
  создаётся задача (или подзадача, если проект продолжается); пропустила → ничего.
  Это ритуал GTD «what's the next action?» на выходе, без принуждения.

### 6.4 Waiting For — быстрый перевод

В модалке подзадачи (`task.html:271`) статус `blocked` уже доступен; добавить рядом
опциональное поле `waitingOn` (кого ждём). Для sequential это корректно останавливает
цепочку до снятия блокировки.

## 7. `add-task.html`

- При создании задачи с подзадачами — селектор `subtaskMode` (default parallel).
- Опциональное поле `spawnOnDone.title` («после завершения создать задачу…»).
- AI bulk import: если модель вернула шаги как явную последовательность — проставлять
  `subtaskMode: "sequential"`.

## 8. Критерии приёмки

- [ ] На трекере у задачи с подзадачами видна **строка текущего действия** (текст подзадачи), а не только дата.
- [ ] `sequential`: доступна ровно одна подзадача; после её `done` следующая автоматически становится доступной и всплывает на карточке.
- [ ] `parallel`: доступны все не-done/не-blocked; «следующая» выбирается по `dueDate` → порядку.
- [ ] Подзадача `blocked` не считается доступной; задача с только blocked-подзадачами уходит в фильтр «⏳ Waiting» и не мозолит глаза в активных.
- [ ] `spawnOnDone` при завершении создаёт задачу-преемника; без него — мягкий промпт «Следующее действие?».
- [ ] Старые задачи (без `subtaskMode`) работают как `parallel`, ничего не сломано.
- [ ] `node --check` проходит по изменённым файлам (правило проекта).

## 9. Вне рамок (на будущие волны)

- **Weekly Review** — экран-ревизия: у каждого активного проекта есть живое доступное
  действие? Ловит «зависшие сто лет» дела.
- **Tickler / defer date** — отдельное «показать не раньше даты» (сейчас `nextAction`
  частично закрывает; можно развить в honest deferred-статус).
- Кросс-задачные зависимости (задача A блокирует задачу B) — пока только внутри одной
  задачи через подзадачи + `spawnOnDone`.
